# 小e数码客服智能体 — 设计文档

> 状态：设计已确认；第一版（通用智能体调试台）开发中（2026-10-09）
> 业务场景参考：[Agent项目-电商智能客服（飞书 Wiki）](https://ncnmfdan85y5.feishu.cn/wiki/F5IiwZVoxiEM4Ck1PPXcGntjncg)
> 本文档记录经逐项讨论确认的设计决定，以及每项决定否决了哪些备选方案、为什么。

## 1. 目标与定位

- **定位**：作品集项目，核心链路按生产标准实现。
- **看点**：智能体决策质量、写操作的安全边界、可复现的评测体系、可观测性。不追求基础设施"全家桶"。
- **业务场景**：虚构的数码 3C 品牌旗舰店"小e数码"，几十个 SKU（手机、耳机、充电器、平板等）。选 3C 是因为它的售后规则多，而且大多需要计算：7 天无理由（拆封或激活另算）、15 天质量问题换货、1 年保修、30 天价保、发票、配件与主机分开退。

## 1.1 第一版：通用智能体调试台（不接业务）

第一版只跑通智能体主循环和日志追踪，不涉及模拟电商、售后规则、知识库和坐席。

- **后端**（`services/agent-api`，Python + FastAPI）
  - 自写薄循环：原生函数调用，最大步数、单个工具超时、整体运行超时，支持中途取消。
  - 工具注册机制：Pydantic 定义参数，自动生成给模型的 JSON Schema 并做服务端校验。
  - 护栏钩子：位于"模型决定调用工具"和"工具执行"之间；第一版用它实现"需要确认的工具先暂停，用户确认后再执行"，业务写操作将来直接复用。
  - 5 个探针工具：
    - `get_current_time`：成功路径；
    - `calculator`：参数校验与模型自我修正；
    - `slow_task`：超时与取消；
    - `flaky_task`：报错回填与连续失败停止；
    - `send_notification`：需确认后执行（模拟）。
  - 模型：OpenAI 兼容抽象层，接阿里云百炼（通义千问），显式关闭思考模式；另有本地模拟模型（`LLM_PROVIDER=mock`），按关键词触发探针工具、不计费，用于无 Key 演示和前端开发。
  - 流式：SSE，同时推送回复文本增量和追踪步骤。
- **追踪**：自建，存 Postgres。
  - 层级：会话 → 运行 → 步骤；步骤类型为模型调用、工具调用、护栏拦截。
  - 每步记录输入、输出、耗时、token 和费用估算；每次运行保存配置快照。
  - 字段按 OpenTelemetry GenAI 语义约定命名，预留导出口。
- **前端**（`web`，Vue 3 + shadcn-vue + Tailwind v4），风格参考浅色极简的分组侧边栏布局：
  - 侧边栏分组：对话（新对话、会话历史）、构建（智能体配置、工具列表）、观测（运行记录）；底部卡片显示今日 token 用量和费用。
  - 空状态：光球、大输入框、5 个探针建议按钮。
  - 对话区：流式回复、可折叠工具卡片、确认卡片、停止按钮。
  - 追踪面板：右侧滑出抽屉，显示运行时间线，每一步可展开原始数据。
  - 支持明暗主题。
- **基础设施**：docker compose 只跑 Postgres；后端和前端在开发时本地启动。

## 3. 智能体决策机制

- **单智能体 + 模型原生函数调用**，不用文本格式的 ReAct（"Thought / Action:" 解析脆弱）。
- **主循环自己写**（约两三百行），不引入 LangChain 等框架：
  1. 组装上下文（系统提示词 + 会话工作区 + 历史/摘要 + 用户消息）。
  2. 调用模型；如果返回工具调用 → 交给护栏层 → 执行 → 把结果回填给模型。
  3. 最多 5 步，整体设超时；超出或连续工具失败就触发转人工规则。
- **工具用 Pydantic 定义参数**：同一份模型同时生成给 LLM 看的 JSON Schema，并做服务端校验。
- **意图**：模型每轮输出一个结构化意图标签，只用于数据分析和看板，**不参与路由**。
- **情感**：只作为信号，影响回复语气和"是否主动询问要不要转人工"；不单独触发转人工，也不加表情前缀。

### 3.1 会话状态机

| 状态 | 含义 | 进入条件 |
|-|-|-|
| `bot_active` | 智能体服务中 | 新会话；坐席交还；待确认操作被确认或取消 |
| `awaiting_confirmation` | 有待确认的写操作 | 写类工具生成了提议 |
| `waiting_human` | 排队等人工 | 命中转人工规则 |
| `human_active` | 坐席接管 | 坐席点击"接入" |
| `closed` | 已结束 | 用户结束、超时、坐席关闭 |

状态迁移只由代码执行，不依赖模型去"记住"。`waiting_human` / `human_active` 期间智能体不自动回复。

## 4. 安全边界（护栏层）

护栏层位于"模型决定调用工具"和"工具真正执行"之间。

### 4.1 身份与数据权限

- 前端模拟登录：从种子用户中选择，后端签发 JWT，会话绑定 `user_id`。
- **工具参数里没有 `user_id`**，由工具执行层从会话上下文注入，模型接触不到身份。
- mock-commerce 再校验一次订单归属：订单号不属于当前用户 → 返回"未找到"（双重防线）。
- 访客只能做知识库问答；涉及订单时提示登录。

### 4.2 写操作：模型提议 → 规则裁决 → 用户确认 → 代码执行

1. 写类工具**不直接改数据**，只生成一条"待确认操作"（类型、订单、商品、金额、原因、幂等键）。
2. 能否办理、可退金额由**规则引擎**根据订单状态、签收时间和 `policies.yaml` 计算，不由模型判断。
3. 前端渲染确认卡片；用户点击"确认"后，后端执行并调用 mock-commerce。
4. 超过金额阈值（暂定 500 元，写在配置里）或属于政策例外 → 不执行，转人工并自动建工单。
5. 每个操作都有幂等键（重复提交只执行一次）和审计日志。

### 4.3 转人工规则（满足任一条即触发）

- 用户明确要求转人工；
- 用户投诉；
- 同一问题连续 3 轮未解决；
- 写操作超出阈值或政策范围；
- 连续工具调用失败或主循环超限。

## 5. 工具清单（第一版共 10 个）

| 工具 | 类型 | 说明 |
|-|-|-|
| `search_knowledge` | 只读 | 混合检索知识库，返回带编号的片段供引用 |
| `list_my_orders` | 只读 | 当前用户的订单；参数只有时间范围、状态筛选 |
| `get_order_detail` | 只读 | 订单详情，含物流轨迹 |
| `search_products` | 只读 | 商品价格、库存、规格 |
| `check_after_sales_options` | 只读 | 规则引擎返回可选售后方式（无理由 / 质量换货 / 保修 / 价保），每项含是否可办、原因、可退金额 |
| `get_invoice_info` | 只读 | 发票信息 |
| `propose_after_sales` | 写·提议 | 退货退款 / 换货 / 价保 |
| `propose_cancel_order` | 写·提议 | 仅限未发货 |
| `propose_update_address` | 写·提议 | 仅限未发货 |
| `request_handoff` | 流程 | 转人工，附原因与摘要 |

工单不作为独立工具，由系统在转人工、写操作超阈值时自动创建。
已砍掉：发邮件（无真实场景）、主动推荐商品（营销类，会稀释"售后可靠性"主线）。

## 6. 数据与知识

### 6.1 模拟电商服务（mock-commerce）

- 独立 FastAPI 服务，使用同一个 Postgres 实例中的独立数据库 `commerce`，只通过 HTTP 接口暴露数据，保持真实的系统边界；将来换成真实平台时只需替换适配层。
- **场景化种子数据**：已付款未发货、已发货、签收 3 天、签收 10 天（超出无理由期限）、已拆封或已激活、部分退款、降价触发价保、缺货等，每个场景对应固定用户，评测可稳定复现。
- **故障注入**：超时、5xx、数据不一致，用于测试智能体的降级行为。

### 6.2 唯一政策数据源：`config/policies.yaml`

- 内容：无理由天数及拆封/激活例外、换货期限、保修期、价保天数、运费承担方、退款到账时间、转人工金额阈值等。
- 规则引擎直接读取它；政策类知识库文档由模板从它渲染生成，再人工审语气。
- 改配置 → 重新生成文档 → 重新跑评测，保证"代码算出的结论"和"文档里写的政策"不会打架。

### 6.3 知识库（RAG）

- **硬规则不进 RAG**，由规则引擎计算并通过工具提供。
- **软知识**：商品说明与常见问题（约 20 个 SKU）、使用指南、配送说明等，共 50 到 100 篇；模型辅助生成初稿、人工审核。不抓取京东、天猫原文，只参考结构。
- **检索**：应用层 jieba 分词 + BM25，pgvector 向量检索，合并后重排序。
- **回答必须带引用**（片段编号，前端可展开原文）；依据不足时明确说"不确定"，并提供转人工入口。
- 导入走命令行脚本，不做管理后台。

### 6.4 上下文管理

- 会话内按 token 预算（暂定 8k）保留；超出后把早期轮次压缩成摘要。
- 工具结果先瘦身成精简的结构化字段再交给模型；完整数据进审计日志和追踪记录。
- **会话工作区**由代码维护并每轮注入：当前讨论的订单、待确认操作、转人工次数、情绪趋势。
- 第一版不做跨会话长期记忆；用户画像通过工具实时查询。

### 6.5 存储（初步，M0 细化）

库 `cs`：`sessions`（含状态机字段）、`messages`、`pending_actions`、`audit_logs`、`tickets`、`handoffs`、`kb_documents`、`kb_chunks`（含向量与分词字段）。
库 `commerce`：`users`、`products`、`skus`、`orders`、`order_items`、`shipments`、`after_sales`、`invoices`、`price_history`。

## 7. 模型

- 兼容 OpenAI 格式的模型抽象层；模型、温度、超时、重试全部配置化。
- 主力用国内旗舰模型（通义千问或 DeepSeek，具体版本在 M1 用评测结果选定）；函数调用的温度设在 0 到 0.3。
- 模拟用户和模型评审用**另一家**的模型，避免自评。
- 用评测集对 2 到 3 个模型做横向对比，比较任务成功率、错误操作率、单次对话成本和延迟。

## 8. 评测体系

参考 τ-bench 零售场景的思路，但使用本项目自己的业务数据。

- **用例**：复用场景种子数据；每个用例包含用户画像、目标和期望的最终状态；先做 50 到 100 个。
- **模拟用户**：由模型扮演用户、按目标进行多轮对话，不写死台词。
- **断言优先检查行为**：
  - 调了哪些工具、参数是否正确；
  - 写操作是否先等用户确认；
  - mock-commerce 中的最终状态（售后单是否生成、金额是否正确）；
  - 该转人工时是否转了；
  - 回答是否带引用。
- **对抗用例**：提示词注入、越权查询、诱导越过政策退款、编造不存在的政策。硬性要求：**错误写操作次数 = 0**。
- **辅助指标**：语气与有依据性由模型评审打分。
- **CI 回归**：每次改提示词、模型或工具都跑一遍，命令行输出静态 HTML / Markdown 报告。
- **核心指标**：任务成功率、错误操作率、转人工准确率、有依据率、拒答准确率、单次对话成本、P50/P95 延迟。

## 9. 前端（Vue 3 + shadcn-vue + Tailwind v4 + Pinia）

1. **顾客聊天页**：选择种子用户登录或访客进入；流式回复；待确认操作渲染为确认卡片；引用可展开查看原文。
2. **坐席工作台**：待接入队列；会话与交接摘要；用户订单和智能体操作轨迹；接入、回复、交还给智能体。
3. **运营看板**：只展示真实统计的数据，包括会话量、AI 独立解决率、转人工率及原因分布、待确认操作的确认率和取消率、平均成本与延迟。

## 12. 决策记录

| # | 决定 | 否决的备选方案 | 理由 |
|-|-|-|-|
| 1 | 作品集项目，核心链路按生产标准做 | 真实业务上线、内部演示、课程 | 力气花在智能体质量、安全和评测上 |
| 2 | 单智能体 + 原生函数调用 + 确定性护栏 | NLU 分流 + 智能体兜底、多智能体、LangGraph 状态图 | 参考文档的两套决策机制重叠；分清"模型做什么、代码兜什么" |
| 3 | 写操作：提议 → 规则裁决 → 用户确认 → 执行 | 直接执行、完全只读转工单、人工审批 | 防注入和诱导退款；可写成"错误写操作 = 0"的评测 |
| 4 | 独立的模拟电商服务 | 同库建表、JSON 假数据、真实平台沙箱 | 真实的系统边界；评测数据来源确定 |
| 5 | 会话绑定身份，工具层注入，服务端再校验归属 | 访客验证查单、不做身份校验 | 即使模型被攻破也拿不到别人的数据 |
