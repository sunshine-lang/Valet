来源：Anthropic 的 [skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)。下面保留它关于「怎么写一份技能」的做法。本环境没有子代理、评测脚本和基准查看器，那些步骤不要执行。写好后用 `create_skill` 保存。

## 在本项目里怎么保存

1. 和用户确认技能要做什么、什么时候触发、输出长什么样。
2. 写出 `name`、`description` 和正文。
3. 调用 `create_skill` 保存。它会把技能写到用户技能目录，并出现在技能页。
4. 不要自己编路径去改 `skills/` 里的内置技能。要改已有用户技能时，用同一个 `name` 再调用一次 `create_skill`。
5. 保存后用两三句真实的用户说法，向用户说明这个技能会在什么时候被用到。不要启动评测脚本。

`name` 只能是小写字母、数字和连字符，并且不能以连字符开头或结尾。`description` 必须同时写清「做什么」和「什么时候用」。

## 先弄清意图

当前对话里如果已经有一段工作流（用户说「把这个做成技能」），先从对话里抽出：用过哪些工具、步骤顺序、用户纠正过什么、输入输出长什么样。缺的再问，确认后再写。

1. 这个技能要让模型做到什么？
2. 什么情况下应该触发？用户会怎么说？
3. 期望的输出是什么格式？
4. 要不要准备几句测试说法？结果可以客观核对的（改文件、抽数据、固定步骤）适合写测试说法。风格类的往往不需要。给出建议，让用户决定。

主动问边界、输入输出例子和怎样算做成。不要在这些没对齐时就保存。

## 怎么写 SKILL.md

- **name**：技能标识。
- **description**：这是触发依据。写清它做什么，以及具体在什么情况下使用。所有「何时使用」都放在这里，不要只写在正文。描述写得具体一点，把用户可能提到的说法也放进去。例如不要只写「做仪表盘」，要写「做仪表盘。用户提到仪表盘、数据可视化、内部指标或想展示数据时都使用。」
- **正文**：步骤、例子、边界。命令式来写。解释为什么这样做，少堆砌「必须」。

技能目录一般是：

```
skill-name/
├── SKILL.md          必需。YAML 头（name、description）加 Markdown 正文
├── references/       可选。需要时再读的说明
├── assets/           可选。模板、图片等产出用的文件
└── scripts/          可选。本环境不会执行脚本
```

加载分三层：系统提示里只有 name 和 description；正文在技能被用到时才读入；references 和 assets 只有正文点到才读。SKILL.md 尽量短于 500 行。更长的材料放到 references，并在正文里写明什么时候去读。

技能内容不能让用户感到意外。不要写误导性技能，也不要写用于未授权访问、窃取数据或其他恶意行为的技能。

输出格式可以在正文里给一个固定模板。例子用「输入 / 输出」成对写清楚。

## 保存

调用 `create_skill`：

- `name`：目录名
- `title`：给人看的标题，可空
- `description`：何时使用
- `body`：不含 YAML 头的 Markdown 正文

保存成功后，告诉用户技能名字和它会在什么情况下被用到。
